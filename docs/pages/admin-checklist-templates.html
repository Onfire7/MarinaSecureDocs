Checklist Templates

Build and manage the reusable templates that generate real Checklists — a role-owned template, its ordered sections (each with its own trigger, place attachment, and time rules), and the items inside them.

Purpose

Reached from Admin Home, gated entirely by manage_checklists. Every template belongs to one role — there is no Global or Personal visibility (personal checklists return later as their own feature). Items are copy-on-edit: committing a change to an item's label or config writes a new row (version+1, previous_version link) and repoints the section's link, so checklists generated before the edit keep rendering exactly what they were created from — see Data Model — ChecklistTemplateItem.

Data shown

FieldSourceNotes
Name, assigned roleChecklistTemplate.name / assigned_roleThe role is required; flagged with a warning until set (instances created meanwhile fall back to assigning the triggering user rather than being orphaned).
Viewer rolesChecklistTemplate.viewer_rolesCheckbox list of the other roles — read-only monitoring access.
AssignmentChecklistTemplate.assigned_to_userCheckbox: assign each checklist to whoever triggers it, vs. leave it unclaimed for the role pool.
TriggerChecklistTemplate.trigger_type / trigger_configManual, Clock In/Out, Checkpoint Visit, or Recurring (an RRULE day rule — days only; time of day belongs to Hide until). Checkpoint Visit templates trigger via the checkpoints named on their sections.
Hide until / Due byhide_until_rule / due_byAuthored rules, resolved to concrete timestamps on each instance at creation; present on the template and on every section.
SectionsChecklistTemplate.sections, orderedEach with name, active toggle, its own trigger (Always / Recurring days / Checkpoint scan / Location visit / Asset), one location, checkpoints in that location, assets, its time rules, and its ordered items.

Actions

ActionGatingBehavior
Create / edit / duplicate / delete a templatemanage_checklistsCreated with a placeholder name and opened straight into the builder, where the name field already lives. Duplicate copies the template, its sections, and fresh item rows (restarting at version 1 — the copy has no history). Delete removes the template and its sections but keeps item rows: instance items on already-generated checklists render their label/type/config through them forever, the same way superseded versions survive an edit.
Add / reorder / remove a sectionSame as editing the templateSections are the unit of triggering and place: name edited inline, drag-by-handle reorder, delete confirmed (generated checklists keep their materialized copy). Inactive sections are never added to new checklists.
Set a section's location & checkpointsSameA section has exactly one location, and its checkpoint picker only offers checkpoints in it — changing the location silently drops attachments that no longer match, which is how the invariant holds (checkpoints can't move between locations, so it can't drift afterward).
Add / reorder / remove an itemSameItems live inside sections. A new item's label starts as its type's name and is edited inline; a Door or Lock Check's required Location defaults from its section's location. Reordering writes in place (order is presentation, never a version). Removal unlinks rather than deletes — instance items keep referencing the row.
Edit an item's label or configSameCopy-on-edit: each committed change (blur/save, not per keystroke) writes a new version row and repoints the section. Duplicate copies type and config to the end of the list as a fresh version-1 row.

States & edge cases

  • Template with no assigned role — flagged in the builder; until set, its instances fall back to whoever triggers them, so nothing is ever created unreachable.
  • Deleting a template with in-progress instances — existing instances are unaffected; they're fully materialized rows and their items resolve through the (kept) item rows. Only future triggers stop.
  • Checkpoint Visit trigger with no checkpoints on any section — shown plainly rather than hidden; the template simply never generates a checklist until a section here names one.
  • Asset sections — configurable now, but no runtime event instantiates them yet; the builder says so.

Mobile vs. desktop

Desktop is the primary surface for building a template's item sequence, given the amount of configuration per item. Mobile supports viewing and light edits, but authoring a new multi-item template is a desk task.
