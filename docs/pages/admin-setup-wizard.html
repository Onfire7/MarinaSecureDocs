Marina Setup Wizard

Builds two levels of the hierarchy, their checkpoints, a tour, and a template attachment in one pass — the job that otherwise spans four screens.

Purpose

Reached from Admin Home, gated by manage_locations. Standing up an area means creating containers (docks, boathouse rows, campground loops), their children (slips, sites), a checkpoint per container, a tour over those checkpoints, and a template attached to them. Done through the individual screens that is four contexts and hundreds of interactions; this collapses it into one form and one commit.

The problem it actually solves

Bulk creation elsewhere is deliberately scoped to a single shared parent, because containers are not uniform: neighbouring boathouse rows in a real marina hold different numbers of units and name them differently — BH30-01L zero-padded with left/right suffixes, BH32-1L unpadded, BH35-01 with no suffix at all. A dialog that applies one name list to many parents cannot express that, which is why one doesn't exist.

The wizard's answer is that the shared pattern is a template that references its container. {parent.last} resolves to "A" for Dock A and "B" for Dock B, so a single pattern already covers rows whose prefixes differ. What remains different is the count, which is one number per row and sits directly on the row. Anything else — padding, suffixes, counter mode, even a wholly unrelated scheme — is overridable per row behind that row's Pattern expander.

Steps

StepFieldsNotes
1 · ScopeAnchor, container type, child typeThe anchor is picked with the searchable ancestor-path combobox and is not assumed to be a root — a marina adds a boathouse row under an existing area far more often than it adds a whole property. The step reports how many matching containers already sit under the anchor.
2 · Containers & childrenNew container names, shared pattern, per-row tableContainers already under the anchor are listed alongside newly typed ones. The shared pattern has an Apply to all included rows action; each row then owns its copy. Every row shows a live count of genuinely-new names, a sample, and how many the pattern generated that already exist.
3 · FinishOptional tour, optional template, reviewA tour can be built from every checkpoint this run creates, in any mode. A checkpoint-triggered template can be attached to the same set. The review states exactly what will be created, including how many generated names will be skipped.

Pattern tokens

TokenResolves toExample
{parent}The container's full nameDock A → Dock A
{parent.last}Its last word — usually the disambiguating partDock A → A
{parent.initials}First letter of each wordDock A → DA

Tokens are valid in the prefix and suffix. The counter (numeric or alphabetic, with range, step, and zero-padding) fills the middle, and comma-separated prefixes or suffixes produce every combination — identical semantics to the name generator on Location setup, which shares the same implementation.

Re-runnability

The wizard only ever creates; it never edits or deletes. Every generated name is checked against the names already present under its container and skipped if taken, so running it twice is safe and running it against a partially-built marina fills only the gaps. Adding next season's dock, or extending an existing row from 17 units to 18, is the same flow as the initial build-out — raise the count and the review reports exactly the two new names.

Existing containers are listed unchecked, so a re-run never silently reprocesses last season's work; including one is a deliberate act.

Actions

ActionGatingBehavior
Create everythingmanage_locationsWritten in ordered chunks — containers, then children, then checkpoints, then the tour and template links — so anything linked to already exists when the link is written, and a 900-slip marina doesn't go out as one enormous transaction.
Override a row's pattern—Local to the wizard until committed. The count sits on the row; everything else is behind the row's Pattern expander, with a live preview of the names it will create.
Add a checkpoint per containermanage_locationsOn by default for newly added containers, off for existing ones. A per-child checkpoint toggle also exists but defaults off — a checkpoint per slip is rarely wanted, and the label states how many it would be.

States & edge cases

  • Every generated name already exists — the row reports "nothing new" and contributes nothing to the commit. Not an error; it's the expected result of re-running against a finished area.
  • A partial failure mid-commit — because the write is chunked, an error can leave earlier chunks committed. The error message says so, and the remedy is simply to re-run: everything already written is skipped.
  • Container type and child type set to the same type — allowed. Nested same-type locations are legitimate (a boathouse row of boathouses), and the type system's own valid_parent_types governs whether it makes sense.
  • Anchor with no existing containers — normal for a first run; the table starts empty and is filled from the name box.
  • No checkpoint-triggered templates exist — the attach control says so rather than offering an empty dropdown.
  • Undoing an over-generous count — Location setup deletes a Location once nothing depends on it, so freshly-created children can be removed from the leaves up. That is deliberately not a bulk operation, which is why the review step states counts explicitly and each row previews the actual names before commit.

Mobile vs. desktop

Desktop only in practice — the per-row table wants width, and marina build-out is a desk activity. The screen renders on mobile but is not designed for it.
