Location Types & Locations Setup

Define the marina's location hierarchy, lay out its actual docks/slips/buildings, configure checkpoints, and — the piece deferred since Reservations — upload maps and plot locations onto them.

Purpose

Reached from Admin Home, gated by manage_locations. Three nested concerns live here: the type system (what kinds of location exist and how they nest), the actual location instances (the marina's real docks and slips), and now the map-plotting layer that backs the schematic map views on Location list and Reservation calendar/list.

Map upload & plotting

Per the note carried since Reservations, backed by MarinaMap and LocationMapPlacement in Data Model. Every map is scoped to a Location — there's no unscoped "master map." A marina's overview map is scoped to a root Location (a Location with no parent) representing the property itself; a marina must create at least one such root Location before it can upload its first map. Multiple root Locations are supported, for a marina that manages more than one physical property as one instance — each gets its own overview map rather than forcing everything onto a single image.

FieldSourceNotes
Map name & imageMarinaMap.name / imageUploaded layout/diagram — a schematic, not a real-world map.
ScopeMarinaMap.scopeRequired — a root Location for an overview map, or any other Location for a detail map showing just its children.
Plotted rectanglesLocationMapPlacement (location, map, rect)Drag-and-place a rectangle per Location onto the selected map's image; a Location can be plotted on more than one map (e.g. small on a root-level overview, precise on its parent's detail map) with independent coordinates on each.

Actions

ActionGatingBehavior
Create / edit a LocationTypemanage_locations
Create / edit a Locationmanage_locationsIncluding status (only for types that track it), the reservation toggle, and post-reservation status. Selecting a location in the list opens its settings and its children together, rather than requiring a separate edit affordance.
Create many Locations at oncemanage_locationsA newline-separated name list creates one Location per line under a shared type and parent. A name generator composes that list from prefix(es), a numeric or alphabetic counter, and suffix(es) — e.g. BH-A-5L through BH-A-10R — with a live preview; accepting it fills the name list, which stays freely editable so gaps in a series can be removed before creating. An optional toggle also creates a matching Checkpoint at each new Location in the same transaction — the common case for docks and gates, and otherwise a separate trip back through the tree for every one of them. Bulk creation is scoped to a single shared parent by design; Checkpoints handles the across-many-parents case for checkpoints, and differing child counts and naming per parent are a setup-wizard concern rather than something this dialog should try to express.
Delete a Locationmanage_locationsOffered in the selected Location's own panel, and disabled whenever anything depends on it — child Locations, Checkpoints, maps scoped to it, Leases, Reservations, Incidents, Tickets, Notes, or a Boat/Vehicle currently there. The control names what is blocking it, so the order of operations is discoverable rather than guessed. Only LocationMapPlacements cascade: they carry no information once their Location is gone, the same reasoning map deletion already applies. The dependency check is scoped to the one expanded Location, so the tree view doesn't have to load every ticket and reservation in the marina to render.
Add / edit a Checkpointmanage_locationsGUID URL is generated automatically on creation, not user-entered; GPS radius override defaults to the marina-wide default from Marina Settings. A new checkpoint is named after its location (numerically suffixed if that location already has one) and renamed inline if that's wrong — a checkpoint is nearly always "the checkpoint at this location," so prompting for a name the admin just typed is a step for nothing. Along with Checkpoints, this is where the GUID URL can be copied/shared (e.g. to re-generate a lost NFC tag or QR sticker) — it isn't exposed on Checkpoint detail.
Upload a mapmanage_locationsCreates a MarinaMap; the upload form requires picking a Location to scope it to before the upload completes — there's no way to create an unscoped map. Any Location can be picked, but a root Location (no parent) is the natural choice for an overview map. The scope picker is the same searchable, ancestor-path combobox used elsewhere (e.g. plotting), not a plain dropdown — marinas run to thousands of locations.
Replace a map's imagemanage_locationsUploads a new image, relinks the existing MarinaMap.image to it, then deletes the old file. Not an in-place overwrite (file storage has no update permission) — existing plotted LocationMapPlacements are untouched since they belong to the map, not the image.
Delete a mapmanage_locationsRemoves the MarinaMap, its image, and every LocationMapPlacement on it. Confirmation states how many placements will be lost — they aren't recoverable, unlike unplotting one Location at a time below.
Plot a Location on a mapmanage_locationsPicked with the same searchable, ancestor-path combobox used for map scope — a flat dropdown can't disambiguate the "Slip 14" on every dock, and is unusable past a few hundred locations. Already-plotted Locations are excluded from it. Then drag-and-place a rectangle; select it to adjust font size, padding, and rotation. The rectangle's size is intrinsic to its label rather than independently resizable — sizing it is sizing its text and the padding around it.
Unplot a Location from a mapmanage_locationsRemoves just that one LocationMapPlacement — a Location plotted on multiple maps stays on the others.

States & edge cases

  • Deleting a LocationType with existing Locations — should be blocked or require reassigning those Locations first; deleting the type out from under them would leave orphaned records.
  • Deleting a Location with a subtree — blocked rather than cascaded. A dock's worth of slips carries leases, reservations, and check-in history; a single confirm dialog is not adequate consent for destroying all of it, so the subtree must be emptied deliberately from the leaves up.
  • Location not yet plotted on any map — fine; it simply doesn't appear in the schematic map view mode until plotted, per Location list.
  • Detail map for a parent with no children yet — allowed to create ahead of time; just has nothing to plot until child Locations exist.
  • No root Location exists yet — the map upload form's scope picker has nothing appropriate to offer for an overview map; the admin needs to create at least one top-level Location (e.g. a "Marina" or "Property" type with no parent) first. Detail maps scoped to non-root Locations aren't blocked by this — only an overview map needs a root.
  • Multiple root Locations, each with a map — the schematic map view (Location list, Reservation calendar/list) presents them as a top-level choice before drilling in, rather than picking one arbitrarily.
  • Reservation toggle turned off while a Reservation is active — the existing Reservation isn't retroactively invalidated; only future booking through New reservation form is affected, since that form's target picker only offers currently-enabled locations.

Mobile vs. desktop

Desktop is the primary surface, especially for map plotting, which needs precise drag-and-place interaction and screen width to see the whole layout at once. Mobile supports viewing and light field edits (status labels, a checkpoint's GPS override) but not the map-plotting workflow.
