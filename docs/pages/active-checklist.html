Active Checklist

Item-by-item completion of an in-progress Checklist instance — the most interaction-heavy screen in the app, since it hosts all five item-type behaviors.

Purpose

Reached from Checklist list, a checkpoint scan/manual check-in, or a Location-Based Check item opening a nested instance. Presents every Checklist.items entry (via ChecklistItemResult) at once, recording a result per item and writing it locally-first (see Architecture — Database) — nothing here requires connectivity. Items can be completed in whichever order suits the guard; there's no fixed sequence.

Deferred side effects

Incidents, Tickets, and meter readings raised by an item are described as the guard works and only written when the checklist is submitted. That is what makes a completed item editable: reopening one rewrites its own result and nothing else, because there is no Incident to retract, no Ticket to withdraw, and no Asset.meter_reading already bumped off a number still being corrected.

Each carries the timestamp of the moment the guard recorded it, not the moment of submission — a door found open at 02:10 and submitted at 05:45 is reported as found open at 02:10. Ids are assigned when the finding is recorded, so an item's result can reference its own effects before those rows exist and re-submitting cannot duplicate them. Meter-based maintenance rules are evaluated at submit against the value actually submitted, so a corrected reading can't leave behind a ticket raised for a number that was never real.

The consequence worth stating plainly: a checklist left unsubmitted has raised nothing. Its findings live only on the checklist until it's submitted.

States & edge cases

  • Offline throughout — every write here is local-first; leaving and resuming later (even after reconnecting) preserves exact progress with no special handling.
  • Ticket creation from a failed item — the resulting Ticket.source_incident stays null (this isn't an incident-sourced ticket) but ChecklistItemResult.linked_ticket connects it back; see Data Model.
  • Abandoning mid-checklist — status stays In Progress indefinitely; it simply reappears on Checklist list until finished. Anything it recorded — including doors found in the wrong state — stays unwritten until it's submitted, so an abandoned checklist raises no Incidents or Tickets at all.
  • Submit fails — surfaced on the page rather than swallowed, and the checklist stays In Progress so it can be retried; the deferred effects are written in the same transaction that completes it, so a failure leaves neither half applied.

Mobile vs. desktop

The full item list is visible at once on both — items can be completed in whichever order suits the guard, so hiding all but "the next one" would only get in the way. Mobile stacks items in a single column; desktop lays them out two-up.
