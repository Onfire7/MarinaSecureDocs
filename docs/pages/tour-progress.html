Checklists & Tours · Page Specification

Tour Progress

Security-only view of where a guard stands within a Tour — rendered as an inline section of Checklist list, not a separate page. Presentation differs by tour mode, since Randomized mode must not reveal the full remaining route.

Purpose

One section per tour, directly below the open checklists on Checklist list, under a small heading carrying the tour's name, mode, remaining count, and progress bar. A guard typically has exactly one active tour, so a dedicated page put its steps two navigations from where every round starts; /checklists/tours/:tourId now redirects to the Checklist list so old links and bookmarks still land. Read-only progress tracker — actual check-ins happen through Checkpoint check-in or the manual dialog, not here.

Ordering principle: work leads, done recedes — expressed per mode. Linear and Randomized keep visited stops out of their sequence view entirely, collapsing them into a "Visited this shift · N" disclosure; Freeform shows everything but lets color do the backgrounding, since its location containers stay glanceable either way. A header badge ("4 of 6 left" / "Complete ✓") and a progress bar answer the state question before any list is read.

Data shown, by mode

ModeDisplay
LinearThe next stop as a hero card ("NEXT — STOP 3 OF 6", name, location), then the rest of the route in order under "Then". Sequence numbers are positions in the full route, so they stay stable as stops are completed. Visited stops appear only in the collapsed section.
FreeformOne container per parent location — the unit a guard works a round in: finish this dock, move on — holding that location's checkpoints as buttons color-coded by this-shift status: visited green with a ✓, remaining neutral. Color carries the done/left split without hiding either, so freeform has no separate visited disclosure; each container shows its own n/m count, fully-visited containers sink to the bottom and dim, and every button links to its checkpoint. All must be visited before shift end but order is the guard's choice.
RandomizedOnly the currently-available next checkpoint is shown, plus a remaining count. The rest of the set is deliberately withheld so patrol patterns stay unpredictable, per Role Workflows. The collapsed visited section is shown as in the other modes — it reveals nothing about what remains.

Actions

ActionGatingBehavior
Tap a checkpoint (Linear/Freeform)Security roleShows checkpoint detail/location; does not itself perform a check-in — that still requires the scan or manual flow.
View on mapSecurity roleShows the next checkpoint's GPS position relative to the guard's current location.

States & edge cases

  • No active tour — empty state directing the guard back to Checklist list or Dashboard.
  • Tour scope resets per shift — progress is derived from check-ins whose timestamps fall within the current Shift window (association by timestamp, not a direct reference, per Data Model — Shift), so a new shift starts every tour fresh.
  • Read access for managers — a manager reviewing a guard's live progress (e.g. via Reports) sees the same data read-only; not permission-gated in the fixed list, so treat as covered by general view_reports access.

Mobile vs. desktop

Mobile is the primary surface — used in the field mid-round. The inline section renders identically on desktop; a manager watching a guard's progress does so through Reports rather than this guard-scoped view, whose progress is always the signed-in user's own check-ins.
