Checklists & Tours · Page Specification

Checklist List

The guard's work queue — open checklists first, then each tour's remaining checkpoints inline under a small heading, with finished work collapsed into the background.

Purpose

The landing point for the Checklists top-level nav item (see Introduction — Navigation). Surfaces anything generated by a trigger the user needs to act on: clock in/out, checkpoint visit, recurring schedule, or manually started. This page is also where recurring templates become real checklists: there is no server-side scheduler, so the first holder of a template's assigned role to open the page on a matching day creates that day's instance (deterministic id — racing clients converge on one row). Instances still inside their hide_until exist but are filtered out — they aren't anyone's work yet.

Ordering principle: open work in front, completed work in the background. Open checklists render as tappable cards — In Progress before Not Started, since half-done work goes stale in a way unstarted work doesn't — each labelled with its next action ("Continue" / "Start"). Completed checklists collapse into a "Completed · N" section at the bottom, capped to the most recent 15; a glance-back to confirm "that one went through" is all this screen owes, with full history on Checklist detail and in Reports. The earlier design — a four-column status table defaulting to "All" — buried the row needing attention under the shift's completions, which only grow as the night goes on.

Tour sectionsSecurity roleRendered inline below the open checklists, one section per tour under a small heading (name, mode, remaining badge, progress bar) — per Tour progress, which specifies the per-mode rendering. Without an active shift the steps still list, with a note that progress starts with a shift. Not shown to users without the Security role.

States & edge cases

  • Empty state — no checklists currently apply; distinct copy for "nothing assigned right now" vs. "you hold no roles with checklist assignments."
  • Role-pool instances (template's assigned_to_user off) — every holder of the assigned role sees the same unclaimed instance until someone opens (and implicitly claims) it.
  • Nested sub-checklists (spawned by a Location-Based Check item) — excluded via their parent_item link; they're reached through their parent item, not this list.

Mobile vs. desktop

Mobile: one vertical column — open checklists, then tour sections, then the collapsed Completed disclosure. Desktop: checklists and tours in adjacent columns for users with tour access (Security); without it there is no second column, so the freed width goes to information density instead — open-checklist cards flow two per row. The former mobile Checklists/Tours chip tabs are gone either way: with tours inline there is nothing left to switch between.
